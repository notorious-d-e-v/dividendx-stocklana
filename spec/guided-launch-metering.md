# Guided launch metering and admission

21 September 2026. This is the implementation contract for the bounded social-launch profile. It does not promise an available VM to every visitor, set a hard billing cap, or authorize public load testing.

## Limits and ownership

The shared wallet/guided admission ledger allows 16 active reservations and 500 starts per UTC day. The existing six starts per visitor, 30 per observed IP, 30-second visitor creation cooldown, 15-minute hard session lifetime, 90-second provisioning deadline, 2,000 forwarded requests per session, 240 requests per minute, and 120 mutations remain unchanged. The provider still creates a nonpersistent two-vCPU VM from the accepted snapshot with `deny-all` network policy. The separate public-devnet faucet is unchanged.

The global private Blob ledger is authoritative for daily quotas, active reservations, latest visitor/kind ID, provider/runtime identity and lifecycle. New reservations have `meterVersion: 1`; a private `hosted-session-meters-v1/<opaque 32-hex ID>.json` record holds forwarded, minute and mutation counters. The meter binds the session ID, visitor hash, kind, provider name, runtime ID and expiry. It is initialized before global `ready` publication and never recreated during a charge. A matching already-created open meter may be reused by a concurrent readiness probe without zeroing its counters. Missing, malformed, mismatched, closed or uncertain meters fail closed. The old counter fields in a new global `SessionRecord` stay at zero and are **legacy-only diagnostics**, not the usage source for v1 sessions.

Before charging a v1 request, read the global ledger once and require ready, latest ID, owner, kind, runtime identity and unexpired lifetime; read the bound open meter. A conditional per-session write atomically enforces all three request budgets and rechecks meter binding, open state and expiry. After provider lookup, read the small bound meter again immediately before forwarding to the old VM's fixed gateway path. POST requests also reread the global lifecycle record at this final fence, protecting mutations if meter closure failed during an identity incident. Ordinary guided state GETs use one full-ledger read; the 15 tour steps plus `/start` generate 16 forwarded POSTs, while their 40 internal chain transactions are not 40 broker mutations. All normal ready-to-nonready lifecycle writers close the meter first. A close racing after the final check may let an already admitted request complete against the old VM or fail while it stops; it cannot use a replacement. Charges committed before a later failure remain spent; no forwarded mutation is replayed. Concurrent tabs of one session still contend only with each other, while different sessions no longer contend on a global write. Legacy sessions retain global ledger charging and the final global fence.

Explicit reset closes the v1 meter before marking the global record resetting and stopping the old VM. Failure to close aborts the reset before provider stop or new creation, preserving the existing reservation. Expiry, provider-terminal reconciliation, and proxy-observed provider stop also close an initialized meter before changing a ready global record. For an identity failure, the broker attempts meter close, then **still stops and unpublishes the VM if closure fails**; the final global fence blocks subsequent mutations. If stop is uncertain, its global record retains capacity as unknown. A GET already admitted before this transition may only reach the old VM and its response still passes the route's identity validation; it cannot use a replacement. If initialization never published ready, no charge is possible; normal provisioning timeout and conservative provider reconciliation remain in force. Concurrent resets may return different outcomes but can create at most one replacement by global latest-ID and CAS fencing. Unknown provider create/stop outcomes continue to retain capacity conservatively.

Legacy records have no marker and retain the original global-ledger atomic charge path until they expire. A record with an unsupported marker fails closed. Rolling forward needs no migration. **Rolling back the backend to the pre-meter build while v1 sessions are live is unsafe:** that build ignores `meterVersion` and could treat a v1 record's zero global counters as fresh allowance. Keep the meter-aware backend while rolling back frontend only, or drain all v1 VMs for at least 15 minutes and verify none remain before a backend rollback. An old frontend is compatible with a meter-aware backend.

Blob does not automatically delete meters at session expiry. They are small private durable records and may remain after closure or natural expiry, so storage count grows over time until an explicit retention process exists. This release adds no new cron or cleanup routine; a future operator cleanup must identify exact owned paths and preserve evidence and rollback needs. The global ledger's existing tombstone and daily-counter normalization remains unchanged.

## Capacity and cost boundary

With 500 starts/day, records near UTC boundaries and provider-extended tombstones can overlap. A synthetic 1,500-record ledger with full identity lengths and three days of visitor/IP counters serialized to 2,238,782 bytes; the former 1 MiB Blob limit would reject valid admissions. The limit is 3 MiB, leaving roughly 0.9 MiB in that measured case. Exceptional retained records can still exceed it and must fail closed; future larger launches need a sharded lifecycle/admission store rather than silently dropping tombstones.

One full-ledger read per forwarded GET, plus two for POST, remains a throughput and billing limit. Vercel's [private Blob pricing example](https://vercel.com/docs/vercel-blob/usage-and-pricing) charges Function-to-store data transfer and origin transfer on cache misses; the broker explicitly bypasses cache. At an illustrative 1.5 MB ledger, 500 sessions × 100 forwarded GETs move about 75 GB, or about $8 using `iad1` $0.05/GB Blob transfer plus $0.06/GB origin transfer. Sixteen POSTs per completed guided tour add about 24 GB/$2.64 across 500 sessions. At 1,000 GETs/session, the same assumption implies about 750 GB/$82.50 before Sandbox, Function, gateway transfer, or other projects. These are estimates, not measured production usage; the ledger's actual size and guided polling duration dominate. Two-vCPU/four-GB 15-minute Sandbox compute alone is approximately $0.0212 idle-memory floor to $0.0852 full-CPU upper estimate per completed session in `iad1` at [Vercel Sandbox rates](https://vercel.com/docs/sandbox/pricing). The project Sandbox region and team Spend Management controls must be verified separately. A ~$50/day target is an operating goal, **not a hard cap**.

## Verification gates

Unit tests cover 16 distinct simultaneous meter charges without global writes; same-session CAS contention and each request budget; missing/malformed meter; idempotent initialization; legacy sessions; reset ordering and concurrent resets; owner/latest/expiry fences; failed initialization/close; 16/500 admissions; and 1,500-record ledger size. A bounded real-Blob test should use a disposable private UUID-prefixed ledger and meter namespace, synthetic ready records and no VMs. It should record exact counters, global ETag stability, conflicts, busy/503 rate, read/transfer volume and p95 charge latency. A small post-release browser smoke is separate from a social traffic stress test. Never expose private Blob data or provider credentials in evidence.
